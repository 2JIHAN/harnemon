# Supabase Data (supabase-data)

Postgryph의 서명 스킬입니다. 데이터베이스를 건드리는 모든 작업은 이 문서의 기준을 통과해야 합니다.

## 1. 키와 신뢰 경계

- **키마다 신뢰 수준이 다름** — 공개 가능한 익명 키(`anon`)는 브라우저에 노출되어도 되지만, 그것은 오직 RLS가 켜져 있을 때만 안전합니다. 서비스 역할 키(`service_role`)는 RLS를 통째로 우회하므로 서버 환경 변수에만 두고, 클라이언트 번들이나 로그나 오류 응답에 절대 싣지 않습니다.
- **우회는 이유를 적음** — 서비스 역할 키로 데이터에 접근해야 한다면, 왜 RLS 경로로는 불가능한지를 같은 변경 안에 남깁니다. 이유 없이 편해서 쓰는 우회는 결함입니다.
- **클라이언트가 보낸 사용자 식별자를 신뢰하지 않음** — 주체는 검증된 세션에서만 얻습니다. 요청 본문에 담겨 온 사용자 아이디는 입력값일 뿐 신원이 아닙니다.

## 2. 행 수준 보안 (RLS)

- **테이블 생성과 같은 마이그레이션에서 켬** — `alter table ... enable row level security;`를 테이블 정의 바로 뒤에 씁니다. RLS를 켜지 않은 테이블은 익명 키만으로 전부 읽히는 공개 테이블입니다.
- **정책이 없으면 전부 거부** — RLS를 켜고 정책을 하나도 쓰지 않으면 모든 접근이 막힙니다. 이것이 안전한 기본값이므로, 막힌 상태에서 필요한 통로만 하나씩 여는 방향으로 작업합니다.
- **정책은 동작별로 나눠 씀** — `select`, `insert`, `update`, `delete`마다 별도 정책을 씁니다. `for all` 하나로 뭉치면 읽기 조건과 쓰기 조건이 같아야 한다는 제약이 숨어 들어갑니다.
- **`using`과 `with check`의 역할이 다름** — `using`은 기존 행을 볼 수 있는지 판정하고, `with check`는 새로 쓰이거나 바뀐 행이 허용되는지 판정합니다. `update` 정책에 `with check`를 빠뜨리면 자기 행을 남의 것으로 바꿔 넘기는 경로가 열립니다.
- **여러 정책은 OR로 합쳐짐** — 허용 정책(permissive)은 서로 더해지므로, 정책을 하나 추가하는 행위는 언제나 접근을 넓히는 방향입니다. 좁히려면 기존 정책을 고쳐야 합니다.
- **세션 함수는 스칼라 서브쿼리로 감쌈** — 정책 안에서 `auth.uid()`를 그대로 쓰면 행마다 다시 계산됩니다. `(select auth.uid())` 형태로 감싸면 한 번만 계산된 값이 재사용되어, 행이 많은 테이블에서 응답 시간이 크게 줄어듭니다.
- **정책이 참조하는 열에 인덱스를 만듦** — 정책 조건에 등장하는 소유자 열이나 외래 키에 인덱스가 없으면 모든 조회가 전체 훑기로 떨어집니다.
- **정의자 권한 함수는 검색 경로를 고정함** — `security definer` 함수는 `set search_path = ''`를 붙이고 모든 객체를 스키마까지 적어 부릅니다. 검색 경로를 열어 두면 호출자가 만든 동명 객체가 대신 실행될 수 있습니다.

## 3. 마이그레이션

- **한 파일에 한 가지 변경** — 번호를 붙인 파일 하나가 하나의 의도를 담습니다. 이미 적용된 마이그레이션 파일은 절대 고치지 않고, 되돌릴 일이 생기면 새 파일을 추가합니다.
- **확장한 뒤에 축소함** — 스키마 변경은 새 모양 추가, 데이터 채우기, 양쪽 쓰기, 읽기 전환의 순서로 내보내고, 옛 모양 제거는 그것을 쓰지 않게 된 코드가 배포된 다음 회차로 미룹니다. 파괴적인 단계가 그것을 유발한 코드와 같은 배포에 실려서는 안 됩니다.
- **적용 전에 드라이런으로 확인함** — 실제 데이터에 적용하기 전에, 무엇이 바뀌는지 먼저 출력해 보고 그 결과를 사람이 읽어 확인합니다. 특히 `update`와 `delete`는 영향을 받는 행 수를 먼저 세어 예상과 맞는지 대조합니다.
- **되돌릴 수 있는지 명시함** — 모든 마이그레이션은 되돌릴 수 있거나, 되돌릴 수 없다고 명시적으로 적습니다. 되돌릴 수 없는 마이그레이션은 백업과 복구 경로를 함께 적습니다.
- **운영 중인 테이블에 잠금을 거는 DDL을 피함** — 긴 잠금, 전체 재작성, 인덱스 없는 외래 키 추가는 거부합니다. 인덱스는 동시 생성 경로(`create index concurrently`)를 씁니다.
- **제약은 데이터베이스에 둠** — 고유성, 필수 여부, 참조 무결성, 검사 조건은 애플리케이션 코드가 아니라 스키마에 선언합니다. 코드에만 있는 규칙은 다른 경로로 들어온 쓰기를 막지 못합니다.

## 4. 저장소

- **비공개 버킷을 기본으로 함** — 버킷은 비공개로 만들고 서명 URL로만 내려 줍니다. 공개 버킷은 링크를 아는 누구나 영구히 접근할 수 있으므로, 정말 공개해도 되는 자산에만 씁니다.
- **서명 URL의 만료를 짧게 잡음** — 만료 시간은 그 화면에서 실제로 필요한 시간에 맞춥니다. 길게 잡은 URL은 유출되면 그 기간 내내 유효합니다.
- **버킷에도 정책이 필요함** — 저장소 객체 역시 RLS 정책의 적용을 받습니다. 업로드 경로에 사용자 식별자를 넣고, 그 식별자가 현재 주체와 일치할 때만 쓰기가 허용되도록 정책을 씁니다.

## 5. 완료 판정

명령이 오류 없이 끝난 것은 성공의 증거가 아닙니다. 아래를 실제로 확인한 뒤에 완료를 보고합니다.

- 의도한 행이 조회되는지, 그리고 **권한이 없는 주체로는 조회되지 않는지** 양쪽을 확인합니다.
- 마이그레이션 적용 후 스키마가 의도한 모양인지 조회하여 확인합니다.
- 확인하지 못한 항목은 미검증이라고 명시하고, 성공했다고 추정하지 않습니다.
