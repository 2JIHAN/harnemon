# 하네스의 정의 (What is an AI Harness?)

인공지능 코딩 어시스턴트 생태계에서 **하네스(Harness)**의 개념적 정의, 프롬프트와의 근본적 차이, 그리고 하네스가 필요한 공학적 이유를 서술한다.

---

## 1. 하네스(Harness)의 개념 정의

- **정의** — AI 모델이 자의적 판단이나 환각에 빠지지 않고 프로젝트의 규칙, 도구, 검증 절차에 맞춰 일관되게 소프트웨어를 개발하도록 통제하는 **외부 공학적 제어 계층(Engineering Control Layer)**
- **어원** — 야생마를 마차에 연결하여 마부의 제어 하에 달리게 만드는 마구(Harness), 또는 낙하산/안전줄에 몸을 결속하는 안전벨트에서 유래
- **핵심 역할** — 모델의 지능(Brain) 자체를 개조하는 대신, 모델의 입출력 경계선에서 **상시 규칙 주입(Rule)**, **필요 도구 연결(Skill)**, **물리적 차단 게이트(Hook)**를 배치하여 행동 범위를 한정

---

## 2. 프롬프트 vs 에이전트 vs 하네스 비교

| 구분 | **프롬프트 (Prompt)** | **에이전트 (Agent)** | **하네스 (Harness)** |
| :--- | :--- | :--- | :--- |
| **성격** | 단발성 자연어 지시문 | 자율적 판단 및 루프 실행 주체 | 에이전트를 가두고 통제하는 시스템 규격 |
| **비유** | 운전수에게 내리는 구두 명령 | 차를 모는 운전수 (LLM) | 도로의 가드레일, 신호등, 안전벨트 |
| **영속성** | 대화 턴 종료 시 소멸 | 세션 동안 유지 | 저장소 및 Git 수명주기와 영구 결속 |
| **강제력** | 0% (모델이 무시 가능) | 부분적 (모델 내부 추론 의존) | **100% (Git 훅 등 물리적 차단 가능)** |
| **실패 모드** | 지침 망각, 포맷 일탈 | 무한 루프, 자의적 코드 훼손 | 단일 책임 원칙 훼손 시 비대화 발생 |

---

## 3. 단순 프롬프트 엔지니어링이 실패하는 공학적 이유

수백 줄의 프롬프트를 시스템 프롬프트(`CLAUDE.md`, `.cursorrules`) 하나에 때려박는 단일 파일 방식은 프로젝트가 커질수록 필연적으로 붕괴한다.

- **주의력 저하 (Attention Degradation)** — 컨텍스트 윈도우가 커져도 중간에 적힌 복잡한 규칙은 모델의 '바늘 찾기(Needle in a Haystack)' 한계로 인해 망각된다.
- **상시 컨텍스트 비용 폭발 (Token Tax)** — 모든 사소한 질문("이 함수 뭐야?")에도 10,000토큰짜리 전체 규칙이 매 턴 소비되어 API 비용과 지연 시간이 급증한다.
- **물리적 강제력 부재 (Zero Hard Gate)** — 모델에게 "커밋 메시지는 72자 이하로 써라", "설정 파일을 약화시키지 마라"고 아무리 프롬프트로 애원해도, 모델의 확률적 생성 특성상 1~5%의 확률로 규칙을 위반한다.
- **규칙 간 상충 (Rule Collisions)** — 규칙 문서가 한 파일에 모이면 상호 모순되는 지침이 발생하여 모델이 갈피를 잡지 못하고 엉뚱한 결정을 내린다.

---

## 4. 모던 하네스의 3대 필수 구성요소

현대적인 하네스는 단일 프롬프트를 버리고 관심사를 3가지 축으로 물리 분리한다:

1. **상시 규칙 (Rule)** — 매 턴 모델의 눈앞에 상주해야 하는 최소한의 표현 및 행동 제약 (~100토큰 미만)
2. **온디맨드 역량 (Skill)** — 특정 작업(디버깅, 리팩터링, 특정 API 연동) 시에만 동적으로 로드되는 세부 지침서
3. **물리 게이트 (Hook)** — 모델의 지능을 믿지 않고, OS/Git 레벨에서 커밋이나 도구 호출을 거부(`exit 1`)하는 절대 차단선
